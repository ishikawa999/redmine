# Brief: personal-pins

## Problem
Redmineを日常的に利用するユーザーは、頻繁に参照するチケット、Wikiページ、バージョンへ移動するたびに、プロジェクトや一覧、検索、ロードマップを経由する必要がある。既存のプロジェクトブックマークやWatcherは、それぞれプロジェクトへの移動と通知購読を目的としており、ユーザー個人が任意のオブジェクトを手元に置く用途を担っていない。

## Current State
プロジェクトに限定されたブックマーク機能と、通知を目的とするWatcher機能は存在する。一方、チケット、Wikiページ、バージョンを共通して個人用に保存し、通知とは独立して素早く再訪する機能はない。現在の作業ツリーにはチケットとWikiページを対象とする独立した `pins` テーブルの初期実装があるが、バージョン対応を含む仕様上の要求、境界、同時実行時の振る舞いがまだ明文化されていない。

## Desired Outcome
ログインユーザーが、閲覧可能なチケット、Wikiページ、またはバージョンを詳細画面から気軽にピン留め・解除できる。トップメニューのマイページ横から一覧へ移動でき、デスクトップではカーソルまたはキーボードフォーカスを合わせると最近の閲覧可能な項目を最大5件プレビューできる。通常画面の初期描画はプレビュー取得を待たず、権限を失った項目や削除済み項目は表示されない。同じ項目への重複操作や同時操作でもデータ整合性が保たれる。

## Approach
ユーザーに属する独立したポリモーフィック `pins` テーブルを採用する。`user_id`、`pinnable_type`、`pinnable_id` の組み合わせを一意にし、対象種別は許可リストで制限する。この方式は、ユーザー設定へのID列保存より検索性と整合性が高く、通知責務を持つWatcherとも明確に分離できる。競合する追加操作は `create_or_find_by!` 相当で吸収する。

## Scope
- **In**: チケット、Wikiページ、バージョンの個人ピン、各詳細画面からの追加・解除、トップメニューからの一覧導線、最近の閲覧可能な項目を最大5件表示する遅延プレビュー、一覧画面、所有者制御、閲覧権限によるフィルタ、重複防止、通常削除時の関連ピン削除、削除済み対象への耐性、日本語・英語UI、モデル・コントローラ・回帰テスト
- **Out**: 通知購読、共有ピン、チームまたはプロジェクト共通ピン、手動並び替え、フォルダ分類、プロジェクトブックマークとの統合、既存Watcherの変更、API公開、管理者向け管理画面

## Boundary Candidates
- ピンの所有権、対象種別、一意性、対象の生存確認を担う永続化モデル
- ピンの追加・解除・一覧表示と認証認可を担うコントローラ境界
- 対象別の表示名と遷移先を解決するプレゼンテーション境界
- チケット・Wiki・バージョン詳細画面、トップメニュー、および小画面向け一般ナビゲーションへ最小限の導線を組み込むUI境界

## Out of Boundary
- ピン留めによってメールやアプリ内通知を発生させない
- 他ユーザーのピンを閲覧・編集する機能を持たない
- ピンを業務上の優先順位、担当、スター、Watcherとして扱わない
- ポリモーフィック対象に対するDBレベルの外部キー保証は本仕様の責務としない

## Upstream / Downstream
- **Upstream**: Redmineのユーザー認証、Issue/WikiPage/Versionの `visible?` 権限制御、Railsのポリモーフィック関連、既存のトップメニューとレスポンシブナビゲーション
- **Downstream**: 将来のピン対象種別追加、ピンの検索・分類・並び替え、個人ダッシュボードへの表示

## Existing Spec Touchpoints
- **Extends**: なし
- **Adjacent**: 既存のプロジェクトブックマーク、Watcher、Issue/WikiPage/Versionの閲覧権限、ロードマップ、マイページ、トップメニュー。これらの責務や保存形式は変更せず、ロードマップにはピン操作を追加しない

## Constraints
- Rails 8.1およびRedmineの既存実装規約に従い、追加の外部ライブラリを導入しない
- Redmine本体と同じGPLv2-or-laterの範囲で実装する
- `user_id + pinnable_type + pinnable_id` のDB一意制約を維持し、並行追加による一意制約競合を500エラーにしない
- ポリモーフィック関連には対象側外部キーを設定できないため、通常のモデル削除では関連ピンを削除し、直接SQL等で孤児が生じても一覧表示と操作が失敗しないようにする
- ピン一覧では各対象の現在の閲覧権限を必ず評価し、権限を失った項目を漏えいさせない
- デスクトップとレスポンシブUIの既存メニュー構造を壊さない
- 通常画面の初期描画はピンプレビュー内容の取得完了を待たず、プレビューの取得失敗によって影響を受けない
